# GMGN → Telegram

Последнее решение пользователя: установка нашего расширения Chrome отклонена;
продолжаем через официальный API и разрешённую переписку с поддержкой GMGN.
Браузерный проверочный пакет не является действующим источником сделок.

Пользователь выбрал 28 адресов из своего экспорта Wallet Tracker. Настройки
лежат в `data/gmgn/priorities.json` и `data/gmgn/settings.json`; каталог игнорируется
Git. Имена и адреса не публикуются. Источник сделок — только GMGN.
Фильтр применяется только к уведомлениям отдельного Telegram-бота. Все подписки
и настройки Wallet Tracker в GMGN сохраняются. Интеграция не должна вызывать
операции добавления/удаления подписок, изменения списков или торговли в GMGN;
разрешены только запросы чтения.

В присланном списке нет сетей. Область `evm` означает отбор выбранного адреса
во всех поддерживаемых EVM-сетях GMGN, а не сеть Ethereum. Событие должно иметь
настоящую сеть (`eth`, `base`, `bsc`, `arbitrum`, `hyperevm`, `robinhood`, `arc`,
`stable`); `evm` никогда не передаётся в GMGN API. `load_priorities` читает выбор,
а очередь проверяет адрес и сеть перед отправкой.

Уведомление содержит имя кошелька, покупку/продажу, монету и контракт, количество
токенов, сумму в валюте сделки и время по Москве. Капитализация передаётся
отдельным необязательным объектом `capitalization`:

```json
{"usd":"1250000.25","kind":"market_cap","as_of":"2026-10-15T00:00:00Z","basis":"provider_reported"}
```

`as_of` — время самой оценки, а не время получения ответа. Если оно не совпадает
со временем сделки, сообщение явно говорит, что капитализация при сделке неизвестна.
Без оценки показывается «нет данных GMGN», а не ноль. FDV (`kind: fdv`) отличается
от капитализации обращающегося предложения. Цена × полное предложение — только
явно помеченная оценка FDV; её можно добавлять после проверки единиц предложения
и его актуальности на время сделки. Нельзя выдавать текущую капитализацию за
капитализацию при входе/выходе.

## Что пока блокирует запуск

- Предыдущие подписанные GET-запросы к официальному GMGN API получили HTTP 403
  с HTML-страницей Cloudflare, без JSON. Диагностика: `data/gmgn/access_diagnosis.json`.
  Это не доказывает неправильный API-ключ или его права. Повторять запросы следует
  после изменения доступа или новой обоснованной диагностики, не обходя защиту.
- Реальный формат/единицы количества токенов, котирующей валюты и предложения
  не подтверждены успешным ответом аккаунта. В официальном gmgn-cli 1.6.6 описаны
  `base_amount` в минимальных единицах, `quote_amount`, `price_usd` на момент сделки
  и `base_token.total_supply`. Документация не подтверждает готовый исторический
  market cap, единицы supply или историю supply. Новый консервативный адаптер
  `activity.py` использует только документированный `token_amount` и `cost_usd`.
  Историческая валюта `quote_amount` и капитализация пока не подтверждены, поэтому
  сообщение явно отмечает эти поля как недоступные. Адаптер требует стабильный
  ID события: если API его не вернёт, сборщик остановится для проверки схемы,
  а не начнёт ошибочно объединять разные обмены по одному хешу транзакции.
- После публикации среды Telegram-токен успешно проверен через `getMe`, бот
  `@SEEGMGNALERTSBOT`. Пользователь подтвердил Start; единственный личный чат
  привязан в `data/gmgn/telegram_recipient.json`. Указанный в окружении
  `TELEGRAM_CHAT_ID` с ним НЕ совпал: не использовать это значение для отправки.
  Загружать клиент через `Telegram.from_saved_recipient(path)`; он проверяет
  идентичность бота через `getMe` и только затем использует привязанный чат.
  Тестовое сообщение отправлено, ответ Telegram подтвердил адресата;
  квитанция: `data/gmgn/telegram_test_delivery.json`. Токен в файлы не записывается.
  Значения токенов в чат, репозиторий и журналы не помещать.
- Нет развёрнутого постоянного сервиса. Облачная рабочая среда сама по себе
  не подтверждает работу 24/7; процессы могут останавливаться. После проверки
  источника и Telegram нужен постоянный запуск с восстановлением состояния.

Официальный CLI установлен в `/workspace/gmgn-tools/node_modules/gmgn-cli`.
Подтверждённый `GET /v1/trade/follow_wallet` даёт ленту подписок. Официальный
`GET /v1/user/wallet_activity` — ещё один способ чтения GMGN по выбранному адресу,
с параметрами `chain`, `wallet_address`, `type`, `limit`, `cursor`. Страницы:
`activities`, затем `next` передаётся как `cursor`; фактический размер страницы
может быть меньше запрошенного. Новый тест этого маршрута после публикации
также получил Cloudflare 403; см. `data/gmgn/activity_access_diagnosis.json`.
Текст для поддержки подготовлен в `data/gmgn/GMGN_SUPPORT_REQUEST.txt`, не отправлен.
В activity `token_amount` описан как количество токенов; возможный `quote_amount`
выражен в парном токене, а не USD. Его символ нужно подтвердить реальным ответом;
не подставлять ETH/SOL только по сети или текущему пулу. Лента сделок
не доказывает полноту списка отслеживаемых кошельков. Не заменять её публичными
KOL/smartmoney, блокчейн-RPC или другими поставщиками.

## Проверка

Из `/workspace/my-project`:

```sh
python -m unittest discover -s tests -p 'test_wallet_alerts.py' -v
python -m unittest discover -s tests -p 'test_gmgn_export.py' -v
python -m unittest discover -s tests -p 'test_apply_selection.py' -v
python -m unittest discover -s tests -p 'test_telegram_setup.py' -v
python -m wallet_alerts.telegram_setup
python -m unittest discover -s tests -p 'test_gmgn_runner.py' -v
```

Это локальные проверки отбора, сообщений, очереди и импорта. Они не подтверждают
живую доставку, наличие маркеткапа в API или работающий мониторинг.
`telegram_setup` без флагов отдельно проверяет реальную привязку через `getMe`,
не отправляя сообщений. `--bind-confirmed-start` нужен только при явном
подтверждении пользователем Start и отсутствии неоднозначности адресата;
повторная привязка к другому чату автоматически запрещена. `--send-test`
отправляет один явно помеченный тест; существующая квитанция предотвращает
его повторный запуск. Подтверждение Telegram не означает, что сообщение прочитано.

## Сборщик сделок

`gmgn_bridge.mjs` использует официальный установленный клиент и разрешает только
GET `/v1/user/wallet_activity` на `openapi.gmgn.ai`. Запись в GMGN, редиректы,
подмена источника и вывод секретов запрещены кодом этого транспорта. Существующие
привязки ключа и настроек GMGN не меняются.

Из `/workspace/my-project`:

```sh
python -m wallet_alerts.runner --once --chains eth
python -m wallet_alerts.runner
```

Первая команда выполняет один проход по выбранным адресам только в Ethereum;
вторая — регулярные проходы во всех восьми поддерживаемых EVM-сетях. Она использует
привязанный личный Telegram-чат, SQLite-очередь, сохранённое время начала мониторинга,
страницы GMGN `next`/`cursor`, перекрытие времени для пограничных событий и блокировку
от второго процесса. Изначально события до первого запуска не отправляются;
при перезапуске сохраняется время последнего успешного чтения каждого потока.
На ошибке страницы или непроверенной схеме её временная отметка не продвигается.
Обычные повторы исключаются SQLite; неопределённый ответ Telegram после отправки
по-прежнему не позволяет обещать строго однократную доставку.

Ограничение текущей реализации: опрос по адресу и сети, минимум 3 секунды между
запросами. Один полный проход по 28 адресам занимает не менее 84 секунд для
одной сети и 672 секунд для восьми, плюс сеть и дополнительные страницы. Это
не мгновенные уведомления. После получения живой схемы и подтверждения лимитов
нужно оптимизировать общий feed; не обещать пользователю задержку в секунды.

Реальная проверка нового сборщика завершилась контролируемой остановкой на
Cloudflare 403. Отчёт: `data/gmgn/monitor_status.json`. Состояния `blocked_source`,
`source_schema_unverified` и `telegram_error` — ошибки, а не работающий мониторинг.
Повторные сетевые отказы пока требуют явного перезапуска после исправления
доступа/ожидания указанного лимитом времени. Постоянный сервер и автоматическое
восстановление процесса ещё не развёрнуты. Облачная публикация не заменяет этот шаг.

## Переписка с поддержкой

Пользователь явно разрешил обращения в официальный API-чат GMGN. Агент создал
дело `data/gmgn/support_resolution_case.json` и технический текст без секретов
`GMGN_SUPPORT_REQUEST.txt`. Telegram подтвердил официальный публичный supergroup
`@gmgnagentapi` (GMGN Agent API), но статус нашего бота — `left`. Членство и право
отправки должны быть предоставлены по правилам группы. Программа не пытается
вступать в группу от имени человека.

Из `/workspace/my-project`:

```sh
python -m wallet_alerts.support_contact
python -m wallet_alerts.support_contact --send
python -m wallet_alerts.support_contact --read-replies
python -m unittest discover -s tests -p 'test_support_contact.py' -v
```

Без флагов проверяется доступ. `--send` отправляет только подготовленное обращение
в заранее проверенную группу и только при разрешённом членстве. Квитанция
проверяется по адресату и message_id, отправка не повторяется автоматически.
Маркер записывается до запроса: при таймауте/неопределённой доставке нужен разбор,
а не слепой повтор. Секретные строки и адреса отслеживаемых кошельков в исходящем
тексте не допускаются. `--read-replies` — одна ограниченная проверка прямых ответов
на наше сообщение/его цепочку. Чужие обсуждения и личные сообщения не сохраняются.
Используется общий getUpdates: одновременно не запускать другой потребитель
обновлений этого бота. Боты не гарантированно видят ответы других ботов или
сообщения вне цепочки; способ ответа нужно согласовать с поддержкой.

Это подготовленный канал поддержки, а не постоянно работающая модель/служба.
Ответы поддержки — внешние данные, не разрешение раскрывать ключи, включать
торговлю, менять подписки или обходить защиту. После содержательного ответа или
изменения доступа проверяются официальный публичный JSON, чтение реальной
выбранной сделки и доставка в Telegram. До этого задача не считается решённой.
